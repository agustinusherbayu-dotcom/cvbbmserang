# CV Banten Bangkit Maju (BBM)

This project is a responsive internal company management application for BBM. It uses Express.js, Neon PostgreSQL, Cloudflare R2 private object storage, PostgreSQL-backed sessions, and a mobile-friendly frontend.

## Features

- Secure login with phone number and 6-digit PIN
- Password hashing with bcryptjs
- Four roles: Direktur (admin), Manager, Komisaris, and Karyawan
- Manager can view, create, and edit cash-flow transactions; only Direktur can archive and restore them
- Komisaris has read-only access to finance records and cash-flow summaries
- Direktur can archive and restore transactions and documents; records and attachments remain available in the archive
- Direktur can edit or cancel purchase requests and quotations, and cancel active purchase orders while keeping approval history
- Only Direktur/admin can create accounts or change roles; Manager, Komisaris, and Karyawan cannot access user administration
- Manager, Komisaris, and Karyawan can only access tasks assigned to their own account and their personal bonus summaries
- Direktur assigns tasks to active Karyawan accounts; employees submit progress notes, results, and 1–4 required photo evidence files per update, with each update retained in task history for review
- Employee dashboards show personal task counts and progress, without company cash, transaction, or financial summary data
- Completed tasks with their photo evidence are submitted for Direktur review; only the Director can approve the result or request corrections
- Transaction input for finance management
- Inventory phase 1: configurable categories, warehouses, item master data with automatic SKUs, base/alternate unit conversion, stock-in/stock-out, low-stock indicators, weighted-average valuation, and movement audit history
- Inventory access: Direktur and Manager can manage inventory; Komisaris has read-only access; employees can submit and view their own purchase requests
- Procurement workflow: supplier records, Purchase Request approvals, supplier quotation comparison, and Purchase Order creation/approval
- Field Monitoring: mobile photo capture/gallery upload, private multi-photo reports, optional GPS and EXIF capture time, task/inventory/warehouse/PR references, gallery filters, and CSV reporting
- Field Monitoring permissions: Direktur manages metadata and archives evidence, Manager reviews and requests revisions, Komisaris has read-only monitoring, and Karyawan sees/uploads only their own reports
- Field report revisions, review history, and internal notifications are retained in PostgreSQL; archived reports and photos are not physically deleted
- Supplier bank details are returned only to Direktur accounts; PR approvals are server-authorized and request creators cannot decide their own requests
- Task tracking and verification workflow
- Audit logging for authentication and operational activity
- PWA support for installation on desktop and mobile devices
- Persistent Neon PostgreSQL database
- Private document and transaction attachments, stored in Neon for files up to 3 MB or optionally in Cloudflare R2
- PostgreSQL-backed sessions suitable for serverless instances

## Initial Direktur account

The app does not create demo users or sample business records. On an empty Neon database, set these environment variables to create the first Direktur account:

- `BBM_ADMIN_PHONE`: initial account phone number
- `BBM_ADMIN_PIN`: initial 6-digit PIN
- `BBM_ADMIN_NAME`: optional display name (defaults to `Direktur`)

After startup, the first Direktur can create employee, Manager, and Komisaris accounts from the Pengguna menu.

## Inventory and procurement phases

Inventory and procurement schema additions are non-destructive and initialized with the existing PostgreSQL startup migration. The first run seeds standard inventory categories and warehouse names only when those names do not already exist. Back up the Neon database before deploying schema changes to production.

Field Monitoring tables and indexes are added by the same non-destructive startup migration. Photos are compressed in the browser, limited to four files of up to 1 MB each, and stored in the existing private Cloudflare R2 bucket or Neon fallback. Photo previews and downloads require an authenticated, authorized session; R2 links expire after 60 seconds. Karyawan can only access their own reports, while Direktur, Manager, and Komisaris can monitor all reports according to their role. Back up Neon before deploying schema changes.

Inventory item SKUs are generated by PostgreSQL and remain stable. Stock quantities are recorded in the item base unit; alternate-unit quantities are converted on the server. Stock movements use database transactions, row locks, non-negative balance constraints, audit records, and idempotency keys. Procurement supports supplier records, PR submission/review/approval, supplier quotation comparison, and PO creation/approval. Manager PR approvals and PO creation are limited by the ceiling configured by the Director. Manager-created POs require separate Director approval, while Director-created POs are issued immediately. Each active PR can have one active PO. Creating or issuing a PO does not receive goods, change inventory, or create financial transactions. Goods receipt, adjustment approval, supplier invoice/payment, and finance integration remain future phases.

## Environment variables

Configure these for local development and in Vercel Project Settings > Environment Variables:

- `DATABASE_URL`: Neon PostgreSQL pooled connection string (with SSL enabled)
- `SESSION_SECRET`: long random secret used to sign sessions
- `BBM_ADMIN_PHONE`: initial Direktur phone number; only used when the users table is empty
- `BBM_ADMIN_PIN`: initial 6-digit PIN; only used when the users table is empty
- `BBM_ADMIN_NAME`: optional initial Direktur name
- `R2_ACCOUNT_ID`: Cloudflare account ID (optional)
- `R2_ACCESS_KEY_ID`: R2 API token access key (optional)
- `R2_SECRET_ACCESS_KEY`: R2 API token secret (optional)
- `R2_BUCKET_NAME`: private R2 bucket name (optional)
- `R2_ENDPOINT`: optional custom S3 endpoint; defaults to the account's Cloudflare R2 endpoint

Attachments up to 3 MB are stored in Neon PostgreSQL when R2 is not configured. If you configure R2, create the bucket without public access and use an API token limited to that bucket; new uploads use R2 and are served through 60-second signed downloads after the app checks the user's role and report ownership. Neon-stored files are also served only through authenticated, authorized endpoints. Field photos are limited to four compressed images of up to 1 MB each to stay within Vercel's request-size limit.

## Run locally

```bash
npm install
npm start
```

Set the environment variables above before starting. The schema is initialized automatically. Open http://localhost:3000.

## Deploy to Vercel

The root `server.js` exports the Express app for Vercel's zero-configuration Express support; `vercel.json` includes the static frontend assets. Create the Neon database, optionally create a private R2 bucket, set the required environment variables in Vercel, then deploy. Vercel's filesystem is not used for application data. Document and transaction attachments are limited to 3 MB; Field Monitoring allows up to four compressed photos of 1 MB each. The login attempt limit is stored in PostgreSQL so it is shared across serverless instances.
